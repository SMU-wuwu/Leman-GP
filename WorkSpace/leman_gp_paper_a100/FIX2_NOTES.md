## 官方源码中的问题

已读取对应版本的官方源码：
https://github.com/pytorch/pytorch/blob/v2.7.0/aten/src/ATen/native/cuda/DistanceKernel.cu#L123

`cdist_backward_kernel_cuda_impl` 使用以下代码（第130、133、146行）：

```cpp
const int l = y / r_size;
const int l_size = r_size * m;
scalar_t * buff_i = buffer + l * l_size + (r1 * j + i) * m + init;
```

`l * l_size` 两个操作数都是32位int，乘法可能在加到64位指针之前溢出。
本模型中 batch/head 会合并为一维，单个矩阵临时区大小为 `128*128*96 = 1,572,864` 个元素。
第1366个矩阵起，偏移为2,148,532,224，超过有符号32位整数最大值2,147,483,647。

| 每卡batch | batch×head矩阵数 | 原反向缓冲区元素数 | 偏移越过int32范围 |
|---|---:|---:|---|
| 128 | 1024 | 1,610,612,736 | 否 |
| 192 | 1536 | 2,415,919,104 | 是 |
| 256 | 2048 | 3,221,225,472 | 是 |

这一源码缺陷与故障阈值吻合。错误偏移可能写入缓冲区之外并破坏其他已保存张量，因此参数梯度首先出现NaN的位置不能直接证明错误来自该层的公式。
本地没有CUDA设备，未直接追踪服务器越界写入；本版针对已确认的源码索引缺陷修复，不把特定被破坏的张量或GPU指令顺序当作已测量事实。

## 实现

新增 `safe_l1_cdist`，按独立的样本×head矩阵分组调用原始 `torch.cdist(p=1)`。
每次调用的反向缓冲区最多 `2^27` 个元素（FP32为512 MiB），各次调用的索引从零开始。
当前128字符、96维head对应每组85个矩阵，最大临时区133,693,440个元素，远低于int32上限。

每个query仍看到全部key；没有距离近似、平滑、截断、参数变化、额外随机数、优化器梯度累积或训练batch拆分。
保留fix1的FP32自定义层、FP64梯度范数及异常诊断。启动仍自动选择两张GPU共同满足显存预算的批量。

- 完整Manhattan attention的输出、padding和参数梯度与原调用一致。
- 复核官方源码中的32位乘法，并验证16–512每卡batch下每次分组调用的索引范围；大形状的调用范围检查使用meta张量，不宣称CUDA执行通过。
- 复跑模型公式、FP32自定义层、初始化/RNG、损失、异常诊断、字符评价及CPU断点恢复检查。
